# mtproto

Telegram MTProto proxy на хосте `mtproto`, режим fake TLS (секрет `ee…`), порт 443.

Клиенты подключаются по IP (поле `server=` в ссылке). Домен mtproto.ru смотрит на Cloudflare, а не на этот сервер, поэтому проверять прокси и ходить на сервер — только по IP (он в `~/.ssh/config` и в `.env` на web, не в репе).

## Работа

- `./sv mtproto deploy` — поднять или обновить из репы.
- Секрет — в `mtproto/.env` на сервере (шаблон — [.env.example](.env.example)) и в менеджере паролей. Смена секрета = новая ссылка `tg://` для всех, кто пользуется прокси.
- Готовая ссылка для раздачи — `~/mtproto_config.txt` на сервере.
- `~/start-mtproxy.sh` на сервере — старый запуск через `docker run`, не запускать: увидит занятый 443 и поднимет второй прокси.
- Подключённых клиентов видно только изнутри сети контейнера (docker делает DNAT, на хосте `ss` их не показывает):
  ```sh
  nsenter -t "$(docker inspect -f '{{.State.Pid}}' mtproto)" -n ss -tn state established '( sport = :443 )'
  ```

## Запасной план: mtg

`telegrammessenger/proxy` — официальный образ, но последний раз он собирался в феврале 2020. Пока работает, не трогаем. Переходим на [mtg](https://github.com/9seconds/mtg) v2 (поддерживается, умеет только fake TLS), если:

- клиенты перестают подключаться, а сервер жив — алерт «mtproto недоступен из РФ» при работающем контейнере ([docs/alerts.md](../docs/alerts.md));
- образ перестанет запускаться на новом Docker.

Порядок:

1. Отдельный compose `mtproto-mtg/`, поднять на другом порту на том же сервере, проверить своим клиентом.
2. Проверить, принимает ли mtg текущий секрет. Если да — ссылка не меняется; если нет — новая ссылка, разослать.
3. Перевести mtg на 443, старый compose остановить, `hosts/mtproto` поправить.

Если блокируют сам IP, mtg не поможет — нужен второй прокси на другом VPS. Ссылку на него лучше раздать заранее, пока первый работает.
